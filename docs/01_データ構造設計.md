# 診療報酬100項目 暗記アプリ：データ構造設計（STEP 3）

作成日：2026-11-10　対象：令和8年度（2026年度）診療報酬

## 先に結論

- データの正本は **JSONファイル**（分野ごとに1ファイル）に置き、`build.py` で1枚の `index.html` に埋め込みます。作りは医療情報基礎知識検定アプリ（`apps/iryo-joho-kentei`）と同じです。
- **1項目＝1レコード**とし、変わらない固定ID（例：`NY-003`）を付けます。カード（名称→概要、概要→名称など）は項目データから自動で作るので、カードを別に管理する必要はありません。
- 出典は **出典台帳**（`sources.json`）にまとめ、各項目からは出典IDと確認日だけを参照します。
- 学習記録は端末のブラウザ内に、**カードIDをキーにして**保存します。改定で点数や文言を直しても、IDが同じなら学習履歴は残ります。
- 一次情報で確認が済んでいない項目は `draft`（下書き）とし、アプリには出しません。推測で埋めた情報が学習に混ざることを防ぐためです。

## 3. 項目データ（items/*.json）

### 3-1. 項目の例

点数などの数値は STEP 5 で一次情報を確認してから入れます。下の例では値を空欄にしています。

```json
{
  "id": "NY-010",
  "status": "draft",
  "name": "地域包括医療病棟入院料",
  "aliases": ["包括医療病棟"],
  "kubun": "A304",
  "field": "NY",
  "group": "特定入院料",
  "priority": "A",
  "order": 11,

  "summary": "（一言概要。会議で名前が出たときに思い出したい1文。50字以内）",
  "target": "（どんな病院・患者・医療行為が対象か）",
  "requirements": [
    "（主要な施設基準・算定条件。3つまで）"
  ],
  "points": [
    { "label": "（区分名など）", "value": null, "unit": "点", "per": "1日につき", "note": "" }
  ],
  "similar": [
    { "id": "NY-009", "diff": "（相手の項目との違いを1文で）" }
  ],
  "hook": "（覚え方のヒントや、会議での出方。任意）",
  "revNote": "（令和8年度改定での主な変更を1文で。任意）",

  "fy": "R8",
  "sources": [
    { "src": "S01", "loc": "別表第一 A304", "checked": "2026-11-10" }
  ],
  "updated": "2026-11-10"
}
```

### 3-2. 項目一覧

| 項目 | 必須 | 内容 | 使いみち |
|---|---|---|---|
| `id` | ◎ | 分野コード＋連番。**一度付けたら変えず、再利用もしない** | 学習記録と結び付けるキー |
| `status` | ◎ | `draft`（下書き）／`active`（出題する）／`retired`（廃止） | `active` だけを出題する |
| `name` | ◎ | 告示どおりの正式名称 | カードの表面 |
| `aliases` |  | 略称・通称（例：「7対1」） | 検索と、概要→名称カードの正解判定の参考 |
| `kubun` | ◎ | 区分番号（例：A304） | 表示と並べ替え |
| `field` / `group` | ◎ | 分野コード／中分類 | 分野別の出題と習熟度 |
| `priority` | ◎ | A＝最優先、B＝標準、C＝余力があれば | 新規カードを出す順番 |
| `order` | ◎ | 全100項目の通し番号（学習の順番） | 新規カードをこの順に1日4項目ずつ出す（STEP 4 で、週ごとの区切りではなく通し番号にした） |
| `summary` | ◎ | 一言の概要（50字以内） | **暗記の中心**。名称→概要カードの答え、概要→名称カードの問題 |
| `target` | ◎ | 算定の対象 | カード裏面の補足 |
| `requirements` | ◎ | 主要な施設基準・算定条件（3つまで） | カード裏面の補足 |
| `points` | ◎ | 点数。複数の区分がある項目は配列で持つ | カード裏面と点数カード |
| `similar` |  | 類似項目のIDと違い（1文） | 比較モード |
| `hook` |  | 覚え方のヒント | カード裏面 |
| `revNote` |  | 令和8年度改定での主な変更 | カード裏面 |
| `fy` | ◎ | 適用年度（`R8`） | 古い年度のデータが混ざっていないかの検査 |
| `sources` | ◎ | 出典IDと参照箇所と確認日 | カード裏面の最下部に表示 |
| `updated` | ◎ | この項目を最後に直した日 | 改定時の更新漏れの確認 |

### 3-3. 書き方の決まり

- `summary` は「何に対する報酬か」が分かる1文にします。「〜を評価する入院料」「〜した場合に加算」のように、主語と目的が分かる形で書きます。
- `requirements` は細かい数値の完全暗記を目的にしません。会議で話題になる要件（例：看護配置、在宅復帰率、重症度、医療・看護必要度の基準）に絞り、3つまでにします。
- `points` に入れる値は、一次情報で確かめたものだけです。確かめられない値は `null` のままにし、その項目は `draft` のままにします。
- 収益規模（例：100床で年間いくら）は保存しません。アプリが `points` と `per`（1日につき・1回につき など）から目安を計算して表示します。保存すると、点数を直したときに計算結果だけ古いまま残るおそれがあるためです。
- 書籍（完全攻略マニュアル・点数早見表）の本文は書き写しません。リポジトリは一般公開になるためです。書籍は手元での確認用に使います。

## 4. 出典台帳（sources.json）

```json
[
  {
    "src": "S01",
    "title": "診療報酬の算定方法（令和8年厚生労働省告示第○号）別表第一 医科診療報酬点数表",
    "issuer": "厚生労働省",
    "url": "https://www.mhlw.go.jp/...",
    "issued": "2026-03-xx",
    "kind": "告示"
  }
]
```

- `kind` は 告示／通知／疑義解釈／訂正 のいずれかにします。
- 訂正通知や疑義解釈で内容が変わったときは、その文書を台帳に追加し、該当する項目の `sources` に足します。
- 同じURLを項目ごとに繰り返さずに済むので、URLが変わったときも台帳の1か所を直すだけで済みます。

## 5. データ全体の版（meta.json）

```json
{ "fy": "R8", "dataVersion": "2026-11-10", "basis": "令和8年度診療報酬改定（2026年6月施行）" }
```

アプリのホーム画面に「令和8年度版・データ更新日 2026-11-10」と表示します。

## 6. カードの作り方（項目データから自動で作る）

| カードの種類 | ID | 問題 | 答え | 初期設定 |
|---|---|---|---|---|
| 名称→概要 | `NY-010:N` | 正式名称 | `summary`（裏面に対象・要件・点数・出典） | 出す |
| 概要→名称 | `NY-010:S` | `summary` | 正式名称 | 出す |
| 点数 | `NY-010:P` | 正式名称＋区分 | おおよその点数 | 出さない（設定でオンにできる） |
| 比較 | `NY-009+NY-010:C` | 2つの名称 | 違い（`diff`） | 出さない（比較モードで使う） |

- 最初は名称と概要の2種類だけを出します。点数カードは、名称と概要が定着してから設定でオンにします。
- 同じ項目の2枚は同じ日に続けて出さず、1日以上空けます。片方の答えがもう片方のヒントになってしまうためです。

## 7. 学習記録（端末のブラウザ内に保存）

```json
{
  "v": 1,
  "settings": { "newPerDay": 4, "cardTypes": ["N", "S"] },
  "cards": {
    "NY-010:N": { "box": 2, "due": "2026-11-13", "reps": 3, "lapses": 1, "last": "2026-11-10" }
  },
  "log": [ ["2026-11-10T08:12", "NY-010:N", 3, 6] ],
  "daily": { "2026-11-10": { "new": 4, "rev": 12, "ok": 10, "sec": 1420 } }
}
```

- `cards` は各カードの次回の出題日（`due`）と段階（`box`）を持ちます。
- `log` は1回の解答ごとに「日時・カードID・自己採点（1〜3）・回答にかかった秒数」を残します。後から精度の高い方式（FSRS）に切り替えるときに、この記録を使います。
- `daily` は進捗画面の「直近の学習履歴」と継続日数の表示に使います。
- 書き出し／読み込みはこのJSONをそのままファイルにします（バックアップとPC・スマホ間の引き継ぎ用）。

## 8. 出題のルール（段階式の間隔反復）

| 段階（box） | 0 | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|---|
| 次に出すまで | 当日中にもう一度 | 1日後 | 3日後 | 7日後 | 16日後 | 35日後 |

- 自己採点は「言えなかった／あいまい／言えた」の3段階です。
  - 言えた：段階を1つ上げます。
  - あいまい：段階はそのままにし、同じ間隔でもう一度出します。
  - 言えなかった：段階1に戻し、その日のセッションの最後にもう一度出します。
- 「今日の学習」は、期限が来た復習カード → 新規カード（1日4項目）の順に集め、分野が偏らないように混ぜて出します。
- 段階4以上に上がったカードを「定着した」とみなし、進捗画面の習熟度に数えます。

## 9. 改定時の運用

| 変更の種類 | データの直し方 | 学習記録への影響 |
|---|---|---|
| 点数・要件が変わった | 値を直し、`revNote`・`sources`・`updated` を更新する | 履歴はそのまま残る |
| 名称が変わった（中身は同じ） | `name` を直し、旧名称を `aliases` に移す | 履歴はそのまま残る |
| 廃止された | `status` を `retired` にする（データは消さない） | 出題されなくなる。履歴は残る |
| 1項目が2つに分かれた | 新しいIDを2つ作り、旧項目は `retired` にする | 新しい項目として学び直す |
| 新設された | 新しいIDを足す（既存の番号は詰めない） | 新規カードとして出る |

## 10. ビルド時の自動チェック（build.py）

`python build.py` を実行するたびに、次を検査し、問題があれば止めます。

- IDが重複していないか、形式（分野コード＋3桁）が正しいか
- `active` の項目に、必須項目・出典・確認日がそろっているか
- `points` の値が `null` のまま `active` になっていないか
- `fy` がすべて `R8` か（古い年度の混入防止）
- `similar` と `sources` が参照するIDが実在するか
- `summary` が50字以内か、`requirements` が3つ以内か
- 分野ごとの `active` 項目数（目標数との差を表示する）
